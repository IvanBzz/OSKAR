## 0. Главное

- **Недели и месяца в системе нет.** Тренд считается голосованием EMA по 15m/1h/4h/1d. Без согласия дневного ТФ направление получить нельзя, но одного дня тоже мало.
- **Тренд работает как жёсткий фильтр** в 10-м шаге риск-лестницы (`confluence_gate`). Поэтому замена EMA-тренда на W/D относится к классу risk: красный инвариант означает авто-откат (ст. 5 п. 4).
- **Свой журнал EMA-фильтр не подтверждает.** Сравнивал только сопоставимые решения, отклонённые лестницей, у обеих групп медиана R:R 2.0:
  - тренд «mixed»: tp 66 / sl 32 / без исхода 33;
  - «по тренду»: tp 10 / sl 16 / без исхода 17;
  - доля tp среди tp+sl: 67% против 38%, тест Фишера p≈0.012.
  
  **Это не вывод.** Резолвер v1 с известными дефектами (`задачи…md:48,62`), наблюдения сгруппированы по символам и времени. Но и менять EMA на W/D вслепую нельзя: сначала нужно сравнение в shadow.
- **Старшие ТФ используются только для EMA.** 1h/4h/1d уже загружаются, но гэпы и структура на них не считаются. Гэпы этих ТФ и режимы 1h/4h не требуют **ни одного** нового запроса свечей.
- **Главный риск бана — ошибки, а не объём.** Бан 109429 11.10 был за ошибки 109415 (`src/oskar/data/client.py:11-16`). Если 1w/1M просто добавить в контекстные ТФ, вотчлист опустеет: так делать нельзя (подробнее в 3г).
- **Нагрузку можно снизить до любых добавлений.** Кеш, который перезапрашивает свечи только после закрытия бара, сокращает запросы цикла примерно с 65 до 2–3 в минуту. Это экономит больше, чем добавят 1w/1M.

## 2. Что говорит курс (база знаний `vault/library/smc`)

Прочитал 7 из 17 заметок, карту и одну заметку из `levels`.

- **Анализ сверху вниз.** Старший ТФ задаёт тренд, структуру и зоны интереса (POI), младший даёт вход.
  - Свинг: анализ на D1, вход на H4–H1.
  - Интрадей: анализ на H4–H1, вход на M15–M1.
  - Источник: `Старший ТФ дает контекст и POI…md:14-15`.
- **Иерархия.** Структура старшего ТФ главнее младшего; пока её не сломали, движения младшего — коррекции. 80% сделок по тренду старшего ТФ, не больше 20% против и только с подтверждением (`:16-17`).
- **Сокращённая проверка синхрона:** тренд старшего ТФ → премиум/дискаунт → свежая зона интереса → слом структуры на младшем ТФ внутри неё → вход (`:21`).
- **BOS только по закрытию** (`BOS только по закрытию…md:12`). В коде это `structure_close_break=True` (`src/oskar/detect/smc.py:49`).
- **Цепочка слома:** BOS младшего ТФ → смена характера (SMS) старшего → BOS старшего (`Смена характера…md:14-16`).
- **FVG (гэп):**
  - работает как магнит, цели 0.5 (середины гэпа, CE) обычно достаточно;
  - полностью перекрытый гэп мёртв;
  - это дополнительный фактор, а не самостоятельная точка входа;
  - значим, если рождён импульсом с BOS;
  - вход от ближней границы.
  - Источник: `Имбаланс (FVG)…md:15-18,21,23`.
- **Премиум/дискаунт.** Покупки ниже 0.5 диапазона. Диапазон старшего ТФ — для свинга, локальный — для интрадея. Опорные уровни: PDH/PDL, недельные, открытия дня/недели/месяца (`Покупки только в дискаунте…md:12,21-22`).
- **Проверка из 10 пунктов.** Критичны три: зона на старшем ТФ плюс BOS на младшем, премиум/дискаунт, свежесть зоны (`Чек-лист из 10 проверок…md:12-15,21`).
- **Уровни:** «день = уровень, час = сетап, 15/5 мин = вход», поиск уровня начинается с недели (`library/levels/День дает уровень…md:12`).
- **Расхождение с рисунком Ивана.** По курсу цель — 0.5 гэпа. У Ивана продажа S стоит у **дальней** границы (полное закрытие), а после заполнения граница работает как поддержка (покупка B). В дизайне в меню есть все три цели.
- **Месячный ТФ.** В прочитанных заметках отдельных правил нет, кроме открытия месяца и уровней.

## 3. Дизайн

### 3а. Направление по старшим ТФ: 1W + 1D (1M для информации)

**Расчёт для каждого ТФ** (1w, 1d), только по закрытым барам; формирующийся бар клиент отбрасывает (`client.py:285`):
1. `analyze(df_tf, SmcConfig(swing_length=L))` — та же обёртка без заглядывания в будущее (`src/oskar/detect/smc.py:143`). Стартовые значения: L для 1d — 3–5, для 1w — 2–3. Калибровать в shadow; минимум баров — 3·L (`smc.py:118`).
2. Направление — по последнему событию структуры (по `broken_index`). BOS означает «тренд», CHoCH — «переход».
3. Позиция цены 0..1 в диапазоне между последними подтверждёнными swing high и swing low: премиум или дискаунт.
4. Если событий нет: запасной вариант `tf_trend` (EMA) при наличии 60+ баров, иначе `unknown`.
5. Для каждого ТФ записывать: направление, тип события, возраст в барах, уровень инвалидации, позицию в диапазоне, источник (structure / ema / none), число баров.

**Сведение W и D** (месяц не голосует):

| W | D | Итог | Политика (предложение) |
|---|---|---|---|
| bull | bull | bullish, совпадают | только лонги |
| bear | bear | bearish, совпадают | только шорты |
| bull | bear (или bear/bull) | конфликт: дневная коррекция внутри недельного тренда | P1: не торговать (как сейчас при mixed). Когда D даст CHoCH обратно, они совпадут. Контртренд по D — только отдельной shadow-когортой |
| unknown | X | X, с флагом `w_unknown` | как при совпадении, но с пометкой |
| X | unknown | unknown, тогда старый `multi_tf_trend` | без изменений |

- Квоту «не больше 20% контртренда» жёстким правилом **не делать**. Она строится из собственной статистики системы, а это запрещено ст. 3 п. 1.
- **1M — только информация для Scout:** открытие месяца, high/low прошлого месяца, последнее событие структуры на 1M, ближайшие незакрытые месячные гэпы.
- **Считать оба варианта:** `bias_structure` и `bias_ema`, сравнивать в shadow. Курс за структуру. EMA50 на неделе требует около 60 недель, поэтому у многих альтов EMA-вариант будет `unknown`.
- **Порядок внедрения:**
  1. только журнал;
  2. контекст для Scout;
  3. компонент тренда в `score.py`;
  4. замена `trend_mtf` в `confluence_gate` — только после данных, класс risk.
- **В реплее** бары старших ТФ брать строго с `open_ts + tf ≤ ts решения`.

### 3б. Гэпы старших ТФ как цели

**Новый модуль `detect/gaps.py`.**
- Границы гэпа берём из `smc.fvg` (Top/Bottom, `join_consecutive`). Отметку библиотеки об отработке игнорируем и считаем заполнение сами по барам с i+2. Это согласуется с правилом «гэп известен с закрытия i+1» (`src/oskar/detect/smc.py:15-16`).
- Поля гэпа:
  - заполнение по фитилям и по закрытиям, %;
  - статус: open / touched / ce (≥50%) / closed (100%);
  - возраст в барах;
  - расстояние в % и в ATR;
  - флаг «рождён импульсом с BOS».

**ТФ и окна данных.**
- 1h/4h/1d — данные уже загружены (`cycle.py:142-143`), новых запросов 0. 1w — новый запрос.
- Окна при 260 барах: 1h около 10.8 дней, 4h около 43 дней, 1d около 8.5 месяцев. Более старые гэпы не видны.
- Если гэпы закрываются долго, для 1d/1w надо поднять `limit`. Вживую подтверждено до 1000 баров на запрос (`vault/progress/changelog.md:489`), в метаданных ccxt указано 1440.

**Как используем гэпы.**
1. **Тейки в меню.** Для ближайшего незакрытого гэпа старшего ТФ по направлению сделки:
   - `t-gap-near` — ближняя граница (первое касание);
   - `t-gap-ce` — середина 0.5 (по курсу);
   - `t-gap-full` — дальняя граница (как S на рисунке).
   
   В примечании: ТФ, зона, процент заполнения, возраст. Фильтр достижимости — гэп не дальше `D_max(ТФ, режим)`. `D_max` берётся из измерения; до него опция выключена. Лестница с R:R ≥ 2 всё равно применяется (`config/caps.yaml:21`).
2. **Контекст для Scout.** До трёх ближайших незакрытых гэпов сверху и снизу плюс базовая частота закрытия из измерения. Нужна запись в `STATS_MANIFEST` (ст. 3 п. 2). Данные рыночные, поэтому по манифесту это допустимо (`src/oskar/agents/prompts/STATS_MANIFEST.md:12-19`).
3. **Скоринг, только в shadow.** Плюс, если незакрытый гэп старшего ТФ впереди по направлению сделки. Минус, если близкий встречный гэп стоит позади входа.
4. **Позже: гэп как зона входа** с подтверждением на 15m. Это совпадает с пунктом плана R4–R5 «SH–BOS–RTO» (`задачи…md:54`). Самостоятельным входом гэп не будет (курс).

**Если гэп закрывается долго.** Если вероятность дойти до середины гэпа за горизонт режима ниже `p_min`, гэп не попадает в тейки этого режима. Он остаётся в контексте как «дальний магнит» и может стать целью более длинного режима (связь с 3в).

|---|---|---|---|---|---|
| 1h | TBD | TBD | TBD | TBD | TBD |

Методическое замечание. Гэпы, не закрытые к концу истории, — цензурированные наблюдения, а не «закроются когда-нибудь». Корректная оценка — кривая выживания (Kaplan–Meier) по времени до середины гэпа и до полного закрытия. Для торговли нужна вероятность закрытия за горизонт режима: 3 ч для intraday (`profiles.yaml:13`), 12 ч для swing (`profiles.yaml:23`).

### 3в. Переключение ТФ торгующим агентом (ст. 2)

**Режим** — это связка «ТФ направления / ТФ гэпов-целей / сигнальный ТФ», как в курсе и в словах Ивана:

| Режим | Направление | Зоны и гэпы-цели | Сигнальный ТФ | Duration-stop | Стоп, % | Плечо |
|---|---|---|---|---|---|---|
| scalp-15m | D (+W фильтр) | 1h, 4h | 15m | 3 ч (как сейчас) | 0.5–3 (`profiles.yaml:12`) | ≤8 |
| intraday-1h | D+W | 4h, 1d | 1h | TBD (3–12 ч) | TBD | TBD |
| swing-4h | W (+M инфо) | 1d, 1w | 4h | 12 ч (`profiles.yaml:23`) | 1–5 (`:22`) | ≤5 |

Капсы и вся лестница одинаковые для всех режимов (`caps.yaml:17-22`):
- риск на сделку 1%;
- суммарный риск 5%;
- не больше 3 позиций;
- R:R ≥ 2 после комиссий;
- confidence ≤ 75.

**Варианты.**
- **V1. Режим как опция меню, выбирает LLM.**
  - Детекторы строят до трёх кандидатов на символ.
  - Scout получает их одним вызовом (бюджет `settings.yaml:50-51` не растёт) и выбирает `candidate_id` или отказ. Trader выбирает id опций внутри кандидата.
  - Ст. 2 соблюдается: опции перечислены, параметры детерминированы из `profiles.yaml`, размер позиции считает Python.
  - Риск: LLM может дрейфовать к режиму с самым широким стопом. Защита — counterfactuals по невыбранным режимам. Статистика по режимам — только для Analyst (ст. 3 п. 4).
- **V2. Режим по правилу, без LLM.** Например, W+D совпадают и ATR% на 1d в нормальном диапазоне → intraday/swing; конфликт → только scalp или ничего. Пороги нужно калибровать.
- **V3. Сначала параллельные shadow-режимы**, без LLM и без ордеров, со своей когортой у каждого.

**Рекомендую:** V3, затем V1 с V2 как контролем. Это совпадает с пунктом плана «Trader против фиксированного правила» (`задачи…md:55`).

**Что придётся менять в коде.**
- Цикл по режимам в `_process` (`cycle.py:126-219`) и мемоизация `analyze`.
- **id кандидата должен включать ТФ.** Сейчас id — symbol-bar-direction (`options.py:142`). Бары 1h и 4h, открытые в 00:00, получат одинаковый id, и `INSERT OR IGNORE` молча потеряет решение (`cycle.py:190-203`). Это тот же класс бага, что 82/82 (`options.py:136-139`).
- Пауза между кандидатами (кулдаун) — по паре символ+режим (`cycle.py:113,137-139`).
- Горизонт резолвера — во времени для каждого режима, а не 48 баров сигнального ТФ (`cycle.py:26,244,253`).
- `ProfileLimits` для каждого кандидата: `cycle.py:162-166`, `escalation.py:118`, `executor.py:247-257,321-330`.
- Duration-stop и TTL лимитки для каждой сделки по `trades.timeframe` (`position_monitor.py:532`, `daemon.py:313-314`). Инвариант INV-002 тоже должен брать удержание своей сделки (`src/oskar/ops/invariants.py:197`, `daemon.py:566`).
- Схема: режим и поля старших ТФ в `SetupCandidate`; 1w/1M в `Timeframe`; повышение `schema_version` (ст. 2 п. 4; `schemas.py:19,69`).

- **Цикл:** 20 символов, тик 30 с (`profiles.yaml:17`), TTL из `candles.py:16-23`. Получается примерно 40 (15m) + 20 (1h) + 4 (4h) + 1.3 (1d) ≈ **65 запросов в минуту**.
- **Скан:** около 555 символов по 1h раз в 30 мин, одной пачкой (`shadow_runner.py:45`, `scanner.py:21-22`).
- **Резолвер:** до 40 символов по 15m раз в 5 мин (`shadow_runner.py:47,50`).
- **Троттлинг ccxt:** `rateLimit` 100 мс, cost 1 на запрос свечей, то есть не больше 10 запросов в секунду (ccxt 4.5.75, проверено офлайн). Официальный лимит BingX на IP **не проверен**.

**Почему нельзя просто добавить 1w/1M в контекстные ТФ:**
- **Кеш почти не сработает.** TTL по умолчанию 60 с, а при истории короче 260 баров каждый вызов — промах (`candles.py:24,44`). Это плюс около 40 запросов в минуту, примерно +60%.
- **Символы будут падать.** `compute()` требует 60 баров. На 1M это 5 лет истории, почти у всех символов её нет; на 1w падают символы моложе примерно 14 месяцев. Символ при этом выпадает из всего тика.
- **Можно получить бан.** Если BingX не примет интервал, ошибка попадёт в класс «symbol» (`client.py:98-123`): символ уйдёт в чёрный список на 4 ч (`client.py:39,233-236`), сработает бюджет 6 ошибок за 15 мин и пауза всего эндпоинта свечей (`client.py:237-243`). 1w/1M в маппинге ccxt есть, но на бирже я это не проверял.

**Предложение:**
1. **Кеш по закрытию бара.** Перезапрос только когда `now ≥ open_ts + 2·tf + 5–10 с`. Если биржа ещё отдаёт старый бар — ограниченный повтор через 10–15 с. История короче `limit` считается полной. Итог: цикл с ~65 до ~2–3 запросов в минуту.
2. **1w/1M отдельным путём,** не через `compute`. `limit` 200 для 1w и 60 для 1M. Ошибка по старшему ТФ даёт `bias=unknown` и не отправляет символ в чёрный список.
3. **Мемоизация `analyze`** по (символ, ТФ, ts последнего бара) — экономит CPU.
4. **Прирост от добавок.** 1w/1M — около 40 запросов на каждую смену бара плюс по 2 запроса на каждый новый символ вотчлиста. Сколько символов вотчлист меняет за обновление, не мерил; в худшем случае это около +1.3 в минуту. Гэпы 1h/4h/1d и режимы 1h/4h — 0 новых запросов.
5. **До включения** — один ручной запрос 1w и 1M по одному символу, только с другого IP или при остановленном демоне.
6. **Счётчики запросов и ошибок по ТФ** — в `client.health()` (`client.py:184`).
7. **Офлайн-история для этапа 0б:** 109 символов × 4 ТФ ≈ 440 запросов. Только с другого IP или при остановленном демоне, не чаще 1 запроса в секунду.
